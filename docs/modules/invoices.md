# invoices - "Rechnungen"

- **Purpose**: invoice lifecycle - create, pay, send, cancel via Storno;
  XRechnung export.
- **Routes**: `/invoices`, `/invoices/new` (with its own
  `new/pickers.remote.ts`), `/invoices/[id]`.
- **Remotes**:
  - `invoices.remote.ts`: `listInvoicesRemote`, `getInvoiceRemote`,
    `createInvoiceRemote`, `setInvoiceStatusRemote`,
    `markInvoiceSentRemote`, `sendInvoiceRemote`, `deleteInvoiceRemote`,
    `cancelInvoiceRemote` (creates the Storno-Rechnung).
  - `xrechnung.remote.ts`: EN 16931 XML sidecar download ([[xrechnung]]).
  - Guard `requirePermission('invoices')`.
- **Service**: `document-service.ts` (shared with [[offers]]).
- **Tables**: `documents`, `document_items`, `document_payments`,
  `document_pdfs`, `sent_messages`.
- **Special**:
  - **GoBD**: issued invoices are never deleted; `cancelInvoiceRemote`
    creates a negating `status='storno'` invoice from the `storno`
    number range and chains
    `cancelledByDocumentId`/`cancelsDocumentId`
    ([[adr-015-storno-instead-of-delete]]). The Storno PDF is rendered
    and persisted at cancel time inside `cancelInvoice` (like every
    other document PDF at creation; the view path reads only from the
    cache and would otherwise 404 forever). Since 2026-07 the generic
    `setInvoiceStatusRemote` accepts only
    `created`/`sent`/`paid` - a status can no longer be flipped to
    `cancelled` outside the Storno flow.
  - **Order link** (migration 0037, [[order-invoice-rules]]): invoices
    that bill a work order carry the permanent
    `documents.work_order_id` backlink (Storno documents inherit it);
    cancelling the ACTIVE invoice of an order auto-reopens the order
    (in_progress, time entries un-billed); order-linked invoices are
    undeletable; the invoice detail links back to its Auftrag.
  - **Lifecycle CTAs**: the header CTA follows created → "Versenden" →
    sent → "Als bezahlt markieren". Additionally, "Als bezahlt
    markieren" is available already from `created` as a body action
    (Barzahlung over the counter without a mail round trip).
  - **Keyed detail navigation**: `src/routes/invoices/[id]/+layout.svelte`
    wraps the subtree in `{#key page.params.id}` - the Storno banner
    links between an invoice and its Stornorechnung on the same route,
    and the detail page freezes the id at init, so without the key the
    old document would keep rendering under the new URL.
  - Payments (`document_payments`) with method from the shared
    `PAYMENT_METHODS` constant; covering the gross total flips status to
    `paid`.
  - `reminderLevel` counts sent Zahlungserinnerungen ([[reminders]]).
  - Sending mails the cached PDF ([[pdf-pipeline]], [[smtp-mail]]).
  - **Stock sales**: a vehicle position links the vehicle at document
    level (`documents.vehicleId`) - both the `?vehicleId` preload from
    the stock panel and a manually picked vehicle position set it.
    Marking the invoice paid then triggers
    `transferStockVehicleOnPayment` (buyer FK, `vehicle_sales` row with
    invoice gross + backlink, listing → `sold`; idempotent no-op for
    ordinary repair invoices). See [[inventory]], [[vehicles]].
  - Time entries listed on the detail that stem from a work order
    (`workOrderItemId` set) show an "Auftrag" badge instead of a delete
    action - order-derived rows are read-only everywhere and are
    maintained at the order ([[hours]], [[orders]]).
  - Invoices generated by work-order completion snapshot the executing
    employee into labor positions: "(ausgeführt von NAME)" is appended
    to the position description ([[orders]]).
- **Tests**: `document-service.test.ts`, `xrechnung-service.test.ts`,
  `pdf-service.test.ts`.
