# Modul: Angebote, Rechnungen, Storno, Verkaufsbuch, PDF-Pipeline, XRechnung   (Kürzel: DOC)

Sprache: Deutsch für Fließtext/Tabellen; Code-Bezeichner, Dateipfade, Tabellen-/Spaltennamen bleiben englisch und exakt wie im Code.
Alles muss aus dem tatsächlich gelesenen Code stammen. Keine Vermutungen. Bei Unsicherheit "unklar" schreiben und Fundstelle nennen.
Fundstellen immer als `pfad/datei.ts:zeile`.

Vorbemerkung zum Datenmodell: Angebot (`offer`), Kostenvoranschlag (`cost_estimate`), Auftragsbestätigung (`order_confirmation`) und Rechnung (`invoice`) teilen sich die eine Tabelle `documents` (Diskriminator `type`). Eine Stornorechnung ist **kein eigener Typ**, sondern `type='invoice'` + `status='storno'` mit negierten Beträgen (`src/lib/server/services/document-service.ts:419-584`). Zahlungserinnerungen liegen in der eigenen Tabelle `reminders` (eigenes Modul REM; hier nur der PDF- und der Detailseiten-Bezug).

## 2. Remote Functions und Endpoints

Gemeinsame Item-Schemas (identisch in beiden Remotes): `itemSchema` `src/routes/offers/offers.remote.ts:46-55` / `src/routes/invoices/invoices.remote.ts:44-53`:
- `description`: `pipe(string(), trim(), maxLength(500))` — **keine deutsche Meldung**, kein `minLength`
- `quantity`: `number()` — keine Grenzen, kein Vorzeichen-Check
- `unit`: optional `pipe(string(), trim(), maxLength(20))`
- `unitPriceNet`: `moneySchema` (`number('Bitte geben Sie einen Betrag ein.')`, `minValue(-1e9,'Der Betrag ist zu klein.')`, `maxValue(1e9,'Der Betrag ist zu groß.')`, `src/lib/server/db/validation.ts:187-191`) — **negative Preise erlaubt**
- `discountPercent`: optional `number()` — **unbegrenzt** (>100 oder negativ möglich)
- `taxRate`: `number()` — **beliebiger Satz** serverseitig
- `kind`: optional `pipe(string(), maxLength(20))` — nicht auf `article|service|material|pass_through|vehicle` beschränkt
- `articleNumber`: optional `pipe(string(), trim(), maxLength(50))`

Kopfschemas: `issueDate`/`serviceDate`/`dueDate` = `pipe(string(), trim(), maxLength(10))` — **kein Datumsformat-Check** (`dateStringSchema` aus `validation.ts:168` wird nicht verwendet); `header`/`footer` = `longTextSchema` (max 10.000, deutsche Meldung `validation.ts:129-133`); `notes` = `notesSchema` (max 2.000, `:123-127`); `paymentMethod` = `paymentMethodSchema` = `optional(picklist(PAYMENT_METHODS,'Bitte eine gültige Zahlungsart wählen.'))` (`:164-166`); `items` = `pipe(array(itemSchema), maxLength(500))`; `customerId`/`vehicleId` = `optional(idSchema)` (`idSchema` = string 1..64 trim, `:28`).

## 7. Nebenwirkungen

- **E-Mails**: `sendDocumentEmail` (`src/lib/server/services/mail-service.ts:238-324`): Vorlage aus `mail_templates` nach `key` = `invoice`/`offer`/`cost_estimate`/`order_confirmation`; Empfänger = Kunden-E-Mail (Name = Firma oder Vor-/Nachname); PDF-Anhang für diese vier Typen via `getOrRenderDocumentPdf` (Render-Fallback!); `sent_messages`-Zeile erst `pending`, dann `sent`/`failed` (+`errorMessage`); Fehler → Remote wirft 400 mit SMTP-Text. Zahlungserinnerungs-Mail (Vorlage `reminder_1`) im Reminder-Modul.
- **PDFs**: persistiert bei `createDocument`, `cancelInvoice`, Import, Mail-Fallback; Dateiname `<documentNumber>.pdf`; Viewer-Fragment `#<documentNumber>.pdf`; Sale-Sign/Reifen-Etikett nicht persistiert (Blob-Tab via `openPdfInNewTab`, `src/lib/utils/pdf-download.ts:52`).
- **Exporte**: XRechnung-XML `<documentNumber>.xml` (`application/xml`) per `downloadBase64File` (`pdf-download.ts:78`); DATEV (anderes Modul) liest nur `sent|paid|storno` (`datev-export-service.ts:469`).
- **Nummernkreise**: `invoice`, `offer`, `cost_estimate`, `order_confirmation` (`{N}`), `storno` (`S-{N}`), indirekt `reminder`; Vergabe außerhalb Transaktionen; Public-API-Bestellungen verbrauchen `invoice`-Nummern.
- **Auftrag/Stunden**: `cancelInvoice` öffnet Auftrag wieder und entkoppelt `time_entries`; `completeWorkOrder` (`work-order-service.ts:1015-1160`) erzeugt Rechnung mit `workOrderId`, `dueDate = issueDate + defaultPaymentTermDays`, `serviceDate = heute`, Steuersatz `defaultVatRate`, Arbeitszeit-Positionen `kind 'service'`, Einheit `Std.`, Beschreibung `… (ausgeführt von <Name>)`.
- **Fahrzeugverkauf**: `setInvoiceStatusRemote(paid)` → `sellStockVehicleToCustomer` (Halterwechsel, `vehicle_sales`-Zeile mit `salesPriceGross = grossTotal`, Listing `sold`).
- **Uploads / externe APIs / Webhooks**: keine in diesem Modul (Logo kommt aus Settings).
- **Audit**: keine Audit-Tabelle; Historie nur über Status/Storno-Verkettung und `sent_messages`.

## 11. Offene Fragen an den Architekten

1. **Zahlungsmodell**: Sollen Teilzahlungen, Zahlungsdatum/-art, Skonto und ein Status „teilbezahlt" eingeführt werden (B-302)? Wenn ja: Ableitung `paid` automatisch bei Deckung des Bruttobetrags?
2. **Angebotslebenszyklus**: Ist „versendet" zwingend E-Mail-basiert oder soll persönliche Übergabe (Status-Flip ohne Mail) erlaubt sein? Soll Konvertierung auch aus `created` möglich sein? Ablaufdatum („Gültig bis") mit Status `expired`? (B-312, B-333)
3. **XRechnung-Zielprofil**: Reicht B2B-Sidecar (aktuell) oder wird B2G mit Leitweg-ID, Storno als 381/384, korrekten Steuerkategorien und KoSIT-Validierung benötigt? ZUGFeRD/PDF-A-3 gewünscht? (B-310)
4. **PDF-Vorlagen**: Soll das Legacy-Kfz-Kaufmann-Layout 1:1 erhalten bleiben (inkl. „AT Steuer", Netto-Einzelpreis/Brutto-Gesamtpreis, „KFZ Meisterbetrieb Inh.")? Konfigurierbare Kopf-/Fußtexte, Fonts mit UTF-8 (statt WinAnsi-Sanitizing)? (B-311, B-334)
5. **PDF-Unveränderlichkeit**: Für Rechnungen fix; für Angebote/KV: Neu-Rendern bei Stammdatenänderung erlaubt? Expliziter „PDF neu erzeugen"-Button? Speicherort weiter Postgres `bytea` (ADR-006) oder Objektspeicher? (B-307, B-331)
6. **Public-API-Bestellungen**: Bleiben Web-Bestellungen Rechnungs-Entwürfe mit echter Rechnungsnummer oder eigener Belegtyp/Nummernkreis? (B-322)
7. **Löschregeln**: Angebote (converted/sent) und stornierte Originale wirklich löschbar oder Archiv/Sperre? (B-323, B-324)
8. **Nummernkreise**: Jahres-Reset pro Kind? Lückenlosigkeit als harte Anforderung (dann Nummer erst beim Ausstellen, Transaktionen)? (B-304, B-347)
9. **Rechnungsausgangsbuch**: Welche Status zählen als Umsatz (Abgleich mit DATEV)? Zeitraum frei wählbar (from/to)? CSV-Export? Kunden-/Status-Filter? (B-320, B-321)
10. **Berechtigungen**: Sollen Belegdetails auch ohne `reminders`/`hours`-Recht vollständig sichtbar sein (Nebenkarten ausblenden statt 403)? (B-325)
11. **Beleg-Kopftext**: Feld reaktivieren (UI) oder aus dem Modell streichen? (B-313)
